# MediaProxy — лёгкий HLS-прокси для React Native (iOS + Android): план

> Статус: утверждён. Порядок работ: план → Swift-ядро (собирается) → Kotlin-ядро → TS-оболочка →
> тесты Android и фиксы (1 фикс = 1 коммит). Локальная сборка: Swift — на macOS (CocoaPods/Expo);
> Android/Kotlin — JDK 17 + Android SDK + кэш Gradle, без сети (Maven недоступен).

## 0. Коротко

Одна Expo-библиотека (Swift + Kotlin + TypeScript), которая встаёт между плеером и CDN:

```
AVPlayer / ExoPlayer  →  http://127.0.0.1:<port>/s/<sid>/<b64(origin)>/<name>.<ext>  →  наш прокси  →  CDN
```

Прокси сам: держит заголовки/Cookie/Referer сессии, распознаёт HLS по содержимому (а не по `.m3u8`),
переписывает плейлисты на loopback, качает сегменты на диск, отдаёт Range, греет окно вперёд,
ретраит/дожимает, ограничивает и чистит кэш, переживает фон. JS управляет политикой и получает события;
в медиапуть JS не вмешивается.

Основано на разборе `C:\dev\AnimeApp` (README, `HOSHI-LOGS-BUGREPORT.md`,
`app/docs/KTVHTTPCache-iOS-guideline.md`, `offline-downloads.md`, модули `video-cache`/`local-hls`,
настройки) и на двух независимых адверсариальных ревью (архитектурное и платформенное), результаты
которых вписаны в §12.

## 1. Цель, критерии, границы

### 1.1 Цель

1. Плавное воспроизведение на слабой сети: прокси не держит запрос плеера дольше его собственных
   таймаутов, докачивает с префикса, греет окно вперёд.
2. Полное управление кэшем: лимит, очистка, статистика, состояние по сегментам, вытеснение, защита
   играющего.
3. Ошибки — нативно, политика — из JS: 401/403/410/400, HTML вместо тела, обрывы, смена сети,
   истёкшая подпись.
4. Одинаковое поведение на iOS и Android, включая случаи, которые KTV ломает: варианты CVH без
   `.m3u8`, `EXT-X-MEDIA/MAP/KEY`, cookie на сегменты.

### 1.2 Критерии приёмки (числа)

| № | Критерий | Как мерим |
|---|---|---|
| K1 | Время до первого кадра ≤ 1.5× базы (kodik 720p — 6.9 с ⇒ ≤ 10.3 с; цель ≤ 4 с) | 20 прогонов, лог `[mediaproxy] first-frame`, S3 |
| K2 | 10 мин 720p: 0 ремонтов/перемонтов из-за прокси, кэш ≤ 90 % лимита, ни одного `-1005`-класса | лог + `getStats` |
| K3 | Возврат на 60 с назад в прогретое: первый кадр < 500 мс, 0 запросов в origin | `[mediaproxy] cache-hit` |
| K4 | 3G, 3 % потерь, RTT +1 с: воспроизведение продолжается, докачка с префикса видна в логе, ≤ 3 ошибок, видимых плееру | Network Link Conditioner / `tc` |
| K5 | 403/400 посреди серии: ровно одно событие `onAuthRequired` на поток, 0 повторных запросов этого URL, JS-перерезолв проходит | лог |
| K6 | CVH (вариант без `.m3u8`, UA, без `Origin`): играет через прокси на обеих платформах | лог + S1 |
| K7 | AES-128 фикстура: играет, ключ запрошен 1 раз, на диске ключа нет | тест + `getStats` |
| K8 | Рестарт приложения: `getStats` = диск ±1 %, битые записи усечены, сироты удалены | тест |
| K9 | Фон: iOS 10 мин аудио; Android с foreground-сервисом плеера 10 мин | ручной прогон |
| K10 | В JS во время воспроизведения не идёт тело сегментов (только редкие `getStats`) | Metro/мост |

### 1.3 Что библиотека НЕ делает (осознанно)

DRM/FairPlay/Widevine; live/LL-HLS (детект → прокси без кэша, см. §5.5); полноценный офлайн-менеджер
загрузок (в приложении он свой); JS в медиапути (никакого base64 через мост); переиспользование
подписанных URL между разным контентом; ABR-логика (качество выбирает JS/плеер); PiP/AirPlay-специфика
(AirPlay с loopback не работает — документируем); свой foreground-сервис на Android в v1 (см. §8.3).
`EXT-X-BYTERANGE` — не кэшируем, но проксируем штатно (headers работают, 400 у CVH не будет).

## 2. Архитектура

### 2.1 Топология и почему именно прокси

Плеер — сторонний (`react-native-video`/`expo-video`), точки внедрения своего
`DataSource`/`AVAssetResourceLoader` нет: AVFoundation игнорирует `NSURLProtocol`, у ExoPlayer нет
JS-хука. Единственный универсальный способ доставить заголовки на сегменты (AVPlayer не шлёт Cookie на
HLS — гайдлайн §3) и управлять кэшем — только loopback-прокси с перезаписью плейлиста. Это же даёт
одинаковое поведение обоим движкам.

### 2.2 Компоненты (по одному файлу-ответственности на платформу)

| Компонент | iOS | Android | Ответственность |
|---|---|---|---|
| Модуль | `MediaProxyModule.swift` | `MediaProxyModule.kt` | API Expo, события, конфиг |
| Движок | `ProxyEngine.swift` | `ProxyEngine.kt` | синглтон: сервер, сессии, конфиг, поколение |
| Сервер | `HttpServer.swift` (или GCDWebServer) | `HttpServer.kt` (или NanoHTTPD) | loopback, Range, keep-alive, выдача |
| Загрузчик | `OriginClient.swift` (URLSession) | `OriginClient.kt` (OkHttp) | запросы, таймауты, ретраи, префикс |
| Кэш | `CacheStore.swift` | `CacheStore.kt` | журнал, лимит, эвикция, refcount |
| HLS | `PlaylistRewriter.swift` (чистая) | `PlaylistRewriter.kt` (чистая) | детект, разбор, перезапись |
| Политика | `RetryPolicy.swift` (чистая) | `RetryPolicy.kt` (чистая) | бюджеты, коды, решение «кэшировать/нет» |
| TS | `src/index.ts`, `src/types.ts` | — | типы, обёртка, документация |

### 2.3 Сессии, `cacheKey` и адресация

- `resolve(origin, {cacheKey, headers, cache, prewarm})` создаёт **сессию**: `streamId` (128 бит, в URL)
  + **кэш-идентичность `cacheKey`** (стабильная, от JS: `t<id>|p-<player>|v-<voice>|e<ep>|q<quality>`).
- `streamId` — только адрес сессии в loopback-URL. Кэш ключуется **не** по нему, а по `cacheKey` +
  отпечаток плейлиста + индекс сегмента. Поэтому перерезолв (штатный ремонт, failover) **не теряет
  прогретое** — главный фикс против повторения текущего поведения.
- Заголовки принадлежат сессии. Глобального словаря нет — гонка «URL выдан, заголовки заменены»
  невозможна.
- В `resolve` — асинхронная **предзагрузка плейлиста** (master или сразу вариант, что дали) и первых
  1–2 сегментов; сам `resolve` синхронный и не бросает исключений (нужно приложению: вызов в `useMemo`).
- Максимум 4 активных сессии, LRU-освобождение; `release(streamId)` отменяет префетч и прекэш,
  завершает текущие ответы.
- Сервер поднимается один раз на процесс (`start()` при загрузке приложения), держит порт, имеет
  счётчик `generation`. Перезапуск → событие `onServerState`, JS перерезолвит. Фиксированный «запасной»
  порт (как 8080 в `local-hls`) запрещён.

### 2.4 Поток одного сегмента

```
1. resolve(): сессия, loopback-URL, фоновая предзагрузка плейлиста
2. плеер просит /s/<sid>/<b64>/<name>.<ext>  (Range: bytes=0-)
3. сервер: сессия → cacheKey → плейлист (из памяти) → индекс сегмента
4. кэш: есть complete → сразу 200/206 из файла
5. нет → загрузчик (single-flight): GET с headers, Range: bytes=<prefix>-, Accept-Encoding: identity
6. ответ origin: заголовки + первый чанк → тогда и только тогда отдаём статус плееру
   (200/206 по факту), Content-Length = totalLength, тело = диск[..] по мере роста
7. загрузчик пишет на диск независимо от сокета (backpressure не останавливает запись);
   писатель ждёт на condition (writtenBytes/expectedTotal), а не на EOF файла
8. конец → complete, журнал, prefetch-окно вперёд
9. обрыв → абортивное закрытие сокета (RST), префикс сохранён; следующий Range плеера
   продолжает с префикса; ничего «короткого и успешного» не отдаём никогда
```

### 2.5 Потоки, блокировки, владельцы

- Loopback-сервер: приём + поток на соединение (или потоковая модель библиотеки), **без лимита 8**.
  Нужно ≥ 32 + backlog: AVPlayer держит 4–6 соединений и переоткрывает их. Лимит — только на origin.
- Origin: интерактивных 4, префетч 2, плейлисты — вне очереди (они и так из памяти после prewarm).
- Загрузка: один владелец на ключ `(cacheKey, variantId, segmentIndex)`; refcount = читатели +
  намерение prefetch; отмена — «N секунд без читателей и вне окна prefetch»; проба плеера
  `bytes=0-1` не убивает загрузку.
- Кэш: один мьютекс на стрим (решение об эвикции и refcount — в одной критической секции),
  отложенный `unlink` (никогда не удаляем файл с `writers>0`), журнал — под тем же мьютексом.
- Все ожидания — с таймаутом и широковещательным событием `failed` на condition: иначе сокет плеера
  повиснет до своего таймаута.
- Потоки/очереди не блокируют JS-поток и main thread.

## 3. Публичный API (TS)

```ts
export type Config = {
  enabled: boolean;                 // true
  maxCacheMB: number;               // 512 (единый бюджет, см. §7.2)
  minFreeDiskMB: number;            // 2048 — меньше не кэшируем
  maxSessions: number;              // 4
  prefetchSeconds: number;          // 30
  prefetchMaxSegments: number;      // 6
  prefetchConcurrency: number;      // 2
  interactiveConcurrency: number;   // 4
  reqConnectSec: number;            // 5   (у плеера 8–10)
  reqFirstByteSec: number;          // 5
  reqSilenceSec: number;            // 4
  prefetchRetries: number;          // 3
  minSpeedKBps: number;             // 1 (только prefetch/продолжения)
  cooldownSec: number;              // 30 на сегмент
  prewarmSegments: number;          // 2
  debug: boolean;                   // false
};

export type ResolveResult = {
  streamId: string; url: string; cached: boolean;
  reason: string; generation: number;
};

resolve(origin: string, opts?: {
  cacheKey?: string; headers?: Record<string,string>;
  cache?: boolean;            // false = прокси без диска (live/BYTERANGE/отладка)
  prewarm?: boolean;          // true = плейлист + первые сегменты
}): ResolveResult;            // синхронный, никогда не бросает

release(streamId: string): void;
failOpen(streamIdOrProxyUrl: string): { streamId?: string; originUrl?: string } | null;
nudge(streamId: string): { queued: number };       // «догрузи вперёд» для сторожа
setConfig(patch: Partial<Config>): void;
getStats(): { port, running, generation, bytes, maxBytes, freeDiskBytes,
              streams: number, hits: number, misses: number, evictions: number, prefetched: number };
getStreamState(streamId: string): {
  cacheKey: string; cacheable: boolean;
  segments: Array<{ index: number; startSec: number; durationSec: number;
                    cachedBytes: number; complete: boolean }>;
  cachedAheadSec: number;
};
clearCache(streamId?: string): { freedBytes: number };
start(): Promise<{ port: number; baseUrl: string; generation: number; issues: string[] }>;
```

События (все — через Expo `Events`, батчатся, без тел и подписей в логах):

| Событие | Payload | Смысл |
|---|---|---|
| `onError` | `{code, streamId?, url, originStatus?, attempt, retryable, fatal, message}` | Один раз на переход в `failed`, не на попытку |
| `onAuthRequired` | `{streamId, url, originStatus: 400\|401\|403\|410}` | Подпись/сессия/CDN-привязка: нужен перерезолв |
| `onServerState` | `{running, port, baseUrl, generation, reason}` | Старт/рестарт/останов — против B-20 |
| `onCache` | `{type: 'evict'\|'clear'\|'full'\|'reconcile', bytes, maxBytes}` | Смена состояния кэша |

Политика только из JS: всё, что в `Config`, — таймауты, ретраи, окно/конкурентность префетча, лимит,
режим кэша. Натив никогда не ждёт ответа JS.

## 4. HTTP-контракт loopback-сервера

### 4.1 URL и маршруты

```
GET|HEAD http://127.0.0.1:<port>/s/<sid>/<b64url(absoluteOriginUrl)>/<name>.<ext>
```

- Только литерал `127.0.0.1` (не `localhost`: может уйти в `::1`).
- `<name>.<ext>` — расширение **обязательно** и сохраняется: плейлист — `.m3u8`, сегмент — исходное или
  выведенное (`.ts`/`.m4s`, fMP4 при наличии `EXT-X-MAP`). Причина: `AVURLAsset` выбирает демуксер по
  расширению/UTI; KTV специально дописывает расширение. Инвариант — тестом.
- Прочее — `404`. `GET`/`HEAD`; тело запроса читается и отбрасывается (≤ 64 КБ), иначе `400` и закрытие.
- Заголовки запроса плеера, кроме `Range`, игнорируются: заголовки origin берутся только из сессии.
- `Cache-Control: no-store` для плейлистов и ключей. Диагностические заголовки
  `X-MediaProxy-Cache: hit|miss|partial|passthrough` — только при `debug`.
- Таймаут простоя сокета 60 с, лимит заголовков 8 КБ, keep-alive, `SO_NOSIGPIPE`/`MSG_NOSIGNAL`
  (для своего сервера), абортивное закрытие при ошибке посреди тела.

### 4.2 Коды: наружу никогда не отдаём 4xx origin

| Origin | Плееру | Событие | Причина |
|---|---|---|---|
| 200/206 | 200/206 | — | норма |
| 301/302/307/308 | следуем ≤ 5 | — | финальный URL — база плейлиста |
| 400/401/403/410 | **502** | `onAuthRequired` | Media3 4xx = item dead; JS перерезолвит |
| 404 | **502** | `onError` (retryable false) | серия исчезла; решение — JS |
| 429 | 503 + Retry-After (≤ 5 с) | `onError` | уважаем лимит |
| 5xx | 502 | `onError` | повторяет плеер |
| таймаут | 504 | `onError` | опережаем таймауты плеера |
| HTML/пустое тело/TS-мусор | 502 | `onError` | мусор не кэшируется |
| Range вне ресурса | 416 | — | протокол |
| бюджет исчерпан | 502 | `onError` | cooldown 30 с |

### 4.3 Range

`bytes=N-`, `bytes=N-M`, `bytes=-N`; несколько диапазонов — 200 целиком (легально игнорировать).
`Accept-Ranges: bytes`. 206 с `Content-Range: bytes a-b/total`. `HEAD` — те же заголовки без тела; для
неизвестной длины сегмента — пробный `Range: bytes=0-0` в origin. Плейлисты режутся по Range из памяти
корректно (это фикс KTV §7.3).

### 4.4 Таблица состояний префиксного кэша (письменный контракт)

`totalLength` — из origin; `prefix` — непрерывно записанный префикс.

| Состояние | Запрос плеера | Ответ |
|---|---|---|
| complete (`prefix==total`) | любой Range | 200/206 из файла мгновенно |
| `prefix>0`, `start ≤ prefix` | `bytes=start-` | 206, `Content-Range`, диск с `start`, дальше докачка |
| `prefix==0`, `start==0` | `bytes=0-` | 200 после заголовков+первого чанка origin, стрим по мере роста |
| `start > prefix` (дыра) | любой | pass-through из origin с тем же Range, **без кэша** |
| `total` неизвестен (chunked/gzip) | `start==0` | buffer-then-serve до 8 МБ, затем pass-through; без кэша |
| `total` неизвестен | `start>0` | pass-through |
| `Content-Encoding` | любой | buffer-then-serve (плейлист) / pass-through (сегмент) |
| обрыв посреди тела | — | абортивный close (RST), префикс сохранён |
| диск полон/ENOENT | любой | pass-through + событие 1 раз |
| эвикция во время выдачи | — | отложенный unlink, ответ дочитывается |

Правило: **никогда** не отдавать «успешное» тело короче обещанного; при провале — рвать сокет, чтобы
плеер переспросил Range.

## 5. HLS

### 5.1 Детект

Content-Type `mpegurl` → плейлист; иначе расширение `.m3u8/.m3u`; иначе первые 24 байта тела после
BOM/пробелов — `#EXTM3U`. Это чинит `m3u8` без расширения и варианты CVH (`…/video/`), на которых KTV
уходит в медиа-ветку.

### 5.2 Перезапись (нативно, один и тот же код-парсер на обеих платформах)

- Каждый URI-несущий тег: `EXT-X-STREAM-INF` (следующая строка), `EXT-X-MEDIA`, `EXT-X-MAP`,
  `EXT-X-KEY`, `EXT-X-SESSION-KEY`, `EXT-X-I-FRAME-STREAM-INF`, `EXT-X-PART/PRELOAD-HINT`
  (LL-HLS — только детект).
- URI строк-сегментов.
- Резолв относительно **финального** URL плейлиста (после редиректов); относительная ссылка без query
  **наследует query базы** — сознательное отклонение от RFC 3986, совпадающее с
  `src/lib/urlResolve.ts` приложения (иначе CVH/kodik теряют `sig`).
- Абсолютные loopback-URL; расширение сохраняется/дописывается; `CRLF`/порядок/остальные строки —
  байт-в-байт.
- `EXT-X-KEY` (AES-128): ключ проксируется, но **никогда не пишется на диск** (только память сессии,
  `no-store`). Расшифровка — плеером.
- `EXT-X-MAP` — обычный ресурс, кэшируется и префетчится первым.
- Всё дерево (master → вариант → audio-rendition) проксируется рекурсивно.

### 5.3 Качества

Master-плейлист переписывается, но ABR-логики нет: JS уже парсит master сам (`getWatchLinks`, kodik —
по-качественные плейлисты) и передаёт в `resolve` конкретный вариант. Если дали master — прокси отдаёт
его, выбор делает плеер/JS.

### 5.4 Что кэшируем

VOD-медиаплейлист (`EXT-X-ENDLIST`) — да. Отпечаток плейлиста (кол-во сегментов, первый/последний URI
без query, target duration) пишется в журнал; при несовпадении старый каталог кэша по этому `cacheKey`
считается недействительным и становится первым кандидатом на вытеснение (защита от отдачи чужого
контента после смены плейлиста).

### 5.5 Что не кэшируем, но проксируем

Live/event (нет `ENDLIST`), LL-HLS, `EXT-X-BYTERANGE` (плеер шлёт Range — форвардим), DRM
(`METHOD=SAMPLE-AES`, `KEYFORMAT`, FairPlay `skd://`). Прокси и заголовки продолжают работать — это
важно для CVH, где «играть мимо прокси» = 400 без браузерного UA.

## 6. Сеть

### 6.1 Заголовки, Cookie, Referer

- Источник — только сессия. Снимаем hop-by-hop (`Host`, `Connection`, `Content-Length`, `Range` — свой),
  принудительно `Accept-Encoding: identity`, `If-Range` — от кэша.
- `Origin` не добавляем сами; `User-Agent` не подставляем (CVH требует браузерный — приходит из JS);
  `Referer` — как дали.
- Cookie: iOS — `httpShouldSetCookies=false`, `httpCookieStorage=nil`, свой per-session cookie jar из
  `Set-Cookie` + явный `Cookie`-заголовок сессии (без утечки между сессиями и без зависимости от
  `HTTPCookieStorage`); Android — тот же jar на OkHttp. Регистр ключей не нормализуем «по-своему»:
  отправляем как в конфиге.
- Поток привязан к IP (CVH): после смены сети URL не переиспользуем — `onAuthRequired`.

### 6.2 Таймауты: от поведения плеера, а не от наших представлений

Media3 `DefaultHttpDataSource` живёт 8 с connect/read, OkHttp — 10 с. Наши пороги должны быть
**короче**, иначе плеер отвалится первым и наш ретрай будет невидим.

| Кто ждёт | connect | первый байт | тишина между байтами | пол скорости |
|---|---|---|---|---|
| Запрос плеера | 5 с | 5 с | 4 с | **не применяется** |
| Prefetch/продолжение | 10 с | 10 с | 15 с | 1 КБ/с за 15 с |
| Плейлист (prewarm) | 5 с | 20 с | 60 с (общий) | — |

«Пол скорости» для запроса плеера — вреден: 0.6 МБ при 5 КБ/с = 120 с, а плеер уйдёт по таймауту. Пол
скорости оставлен там, где ждёт только наш prefetch. Числа — из `Config`, с тестом «наши таймауты <
таймаутов плеера».

### 6.3 Ретраи и бюджеты

- **Ретраит плеер, а не мы**, для запросов самого плеера: при провале до первого байта отдаём 502/504
  (укладываясь в 5 с) — плеер сам переспросит Range, а префикс уже на диске, поэтому повтор дешевле
  первого раза. Это снимает мультипликатор «наш ретрай × перемонт × перерезолв» (B-04) и не держит
  запрос дольше сторожа (`reloadSec` 18 с).
- Нативно ретраим только: prefetch, продолжения, где байты уже шли, и плейлисты. Бюджет: 3 попытки
  (0.5/1.5/4 с + jitter), общий дедлайн, cooldown 30 с на `(cacheKey, segmentIndex)`. Новый Range от
  плеера счётчик не сбрасывает.
- `onError` — один раз на переход в `failed`, не на попытку.

### 6.4 Ошибки CDN, которые реально встречаются

| Симптом | Детект | Реакция |
|---|---|---|
| 200 + HTML-страница ошибки | Content-Type + первые байты не `#EXTM3U`/`0x47`/`ftyp` | не кэшировать, 502, `onError` |
| обрыв на середине | Content-Length vs префикс | абортивный close, префикс, продолжение |
| 200 вместо 206 на Range | статус + запрошенный Range | сброс записи, один повтор с 0, иначе pass-through |
| пустое тело 200 | 0 байт при Content-Length>0 | 502, `onError` |
| 403/400 на сегменте (UA/подпись/IP) | статус | `onAuthRequired`, без ретраев |
| «кривой» TS (мусор) | синхробайт 0x47 / `ftyp` | не кэшировать, 502 |
| 429 | статус | `Retry-After` (≤ 5 с), 503 |

### 6.5 Смена сети

iOS: `NWPathMonitor`; Android: `ConnectivityManager`. На смену сети: прервать in-flight (код
`NETWORK_CHANGED`), **не** ретраить подписанный URL (IP-привязка), отметить сессии устаревшими и отдать
`onAuthRequired`-совместимое событие. Никакого «абортим и ретраим» — этот ретрай гарантированно
упрётся в 400.

## 7. Кэш

### 7.1 Раскладка и журнал

```
Library/Caches/mediaproxy/v1/<hash(cacheKey)>/
  journal.log     # append-only: header (cacheKey, fingerprint), затем строки
                  #   idx | total | prefix | state | accessedAt | complete
  s000123.bin     # сегменты по индексу
```

- Append-only журнал + компакция при старте (переписать живые записи). Никаких «tmp → rename» на каждом
  сегменте: это ровно класс ошибок B-01 (256 ошибок `.tmp` не существует).
- На старте: файл короче журнала → доверяем файлу (усечь `prefix`); длиннее `prefix` → `truncate` до
  коммита (иначе порванный TS отдаётся как «готовый»); лишние файлы — удалить, сумму пересчитать.
- Храним `totalLength` всегда — без него префикс неотличим от целого.

### 7.2 Лимит, эвикция, активность

- **Один владелец бюджета**: `maxCacheMB` (512 по умолчанию, приложение передаёт свой `videoCacheMB`).
  Никаких третьих чисел; `getStats` отдаёт и лимит, и свободное место на диске.
- Guard: если свободно < `minFreeDiskMB` (2 ГБ) — не кэшируем (pass-through), событие один раз.
- Soft limit 90 % — останавливаем prefetch; hard limit 100 % — не кэшируем новые запросы плеера
  (отдача продолжается).
- Эвикция: пока не влезет, удалять **целые неактивные стримы** по LRU (`accessedAt`). Активный (запрос
  за последние 2 мин) не трогаем; удаление отложенное (refcount: читатели + писатели). Стрим,
  освобождённый только что, — «карантин» 5 мин, чтобы не выбирать его первым (B-12: возврат к серии).
- Внутри стрима сегменты не вытесняем: эпизод потребляется последовательно, а позапись-уровневый LRU
  будет выбивать прогретый хвост.
- `clearCache(streamId?)`; после очистки — `onCache`.

### 7.3 Prefetch и `nudge`

- После разбора медиаплейлиста и после каждого запроса сегмента `i`: окно `[i+1, i+W]`,
  `W = min(6, ceil(30 / avgDuration))`, конкурентность 2, дедуп с плеером (single-flight), приоритет у
  плеера.
- Первые `prewarmSegments` (2) — сразу после плейлиста, до первого запроса плеера (дедуп делает это
  бесплатным; главный выигрыш — манифест, а не сегменты).
- Пауза плеера прокси не видна → окно ограничено (≤ 6 сегментов, ~30 с видео: пауза стоит не больше
  пары МБ).
- `nudge(streamId)` — принудительное окно от последнего запрошенного индекса; используется сторожем
  вместо `warmAhead` из JS.
- Отмена — на `release`, смене качества/эпизода, hard limit, смене сети.

### 7.4 Состояние для UI

`getStreamState` отдаёт массив сегментов (индекс, startSec, durationSec, cachedBytes, complete) и
`cachedAheadSec` — полоса «на диске» в `Watch` перестаёт читать юниты KTV и становится точной.

## 8. Платформы

### 8.1 iOS

- URLSession: `waitsForConnectivity=false`, `httpMaximumConnectionsPerHost=4`, свои cookie/headers,
  стриминг через delegate-чанки.
- Сервер: спайк D1 (§11). Если GCDWebServer — `AutomaticallySuspendInBackground=NO`, эфемерный порт,
  `GCDWebServerStreamedResponse`/кастомный ответ с Content-Length; если свой — BSD-сокеты,
  `SO_NOSIGPIPE`, поток на соединение.
- ATS: `NSAllowsLocalNetworking` (+ только `127.0.0.1`); `start()` делает self-test HEAD на собственный
  сервер и возвращает `issues` (`ATS_BLOCKED`), а не тихо не работает.
- Фон: одна `beginBackgroundTask`-ассерция на время активных загрузок (не на каждый запрос, не дольше
  бюджета), на return-to-foreground — проверка живости listener и `onServerState` при перезапуске.
  Реальная жизнь в фоне — аудио-сессия приложения или PiP; `-1005` при усыплении процесса — ожидаемое
  поведение, лечится перерезолвом.
- AirPlay с loopback не работает — документируем.

### 8.2 Android

- OkHttp: Dispatcher 6 (интерактив 4 + prefetch 2), `connectTimeout` 5 с, `readTimeout` 4–5 с, свой
  cookie jar, `Accept-Encoding: identity` (OkHttp не должен сам добавлять gzip).
- Сервер: NanoHTTPD (уже проверен в `local-hls`) или свой `ServerSocket` (D1); bind `127.0.0.1:0`,
  фактический порт отдаём наружу.
- Cleartext: config plugin добавляет network-security-config **только для 127.0.0.1** (не глобальный
  `usesCleartextTraffic`); preflight `NetworkSecurityPolicy.isCleartextTrafficPermitted("127.0.0.1")` →
  `issues: ["CLEARTEXT_BLOCKED"]`.
- Двойной кэш исключён: при включённом прокси `source.bufferConfig.cacheSizeMB = 0`.
- Doze/сеть: prefetch только при `active`/FGS; на смену сети — §6.5.

### 8.3 Фон: явный контракт

- iOS: работает, пока приложение не усыплено (аудио-сессия/PiP); сервер в процессе; на возврате —
  `onServerState`.
- Android: прокси живёт, пока жив процесс. В v1 **своего** foreground-сервиса нет; корректный фон
  обеспечивается сервисом плеера (`react-native-video` → `showNotificationControls: true`, сейчас в
  настройках `false`). Для движка `expo-video` (кэша и сервиса нет) — либо FGS плеера приложения, либо
  документированное ограничение. Опциональный FGS `dataSync` в библиотеке — решение в M2 по результатам
  S2 (§11).
- В обоих случаях: никакой остановки сервера на `background`, никакого «нового порта» после фона
  (в отличие от KTV), `generation` и событие — если перезапуск всё же случился.

## 9. Интеграция в AnimeApp

1. Пакет ставится как `file:`-зависимость (`C:\dev\MediaProxyLib`), Expo autolinking; config plugin в
   `app.json`.
2. `src/videoCache.ts` сохраняет внешний контракт (`planStream`, `getCacheStats`, `deleteCacheForUrl`,
   `reportPlaybackError`, …), внутри — `MediaProxy`:
   - `planStream(url, {headers, cacheKey}) → {uri, cached, originUrl, reason, streamId}`;
   - `cacheKey` — новый проп из `Watch` (`t<id>|p-<player>|v-<voice>|e<ep>|q<quality>`), иначе
     fallback — origin URL;
   - fail-open: `onError{fatal}` или `reportPlaybackError(uri)` → `failOpen` + перемонт на origin
     **с `source.headers`** (для CVH обязательны).
3. Удалить: `services/warm.ts` (заменяется префетчем + `nudge`), `lib/warmPlan.ts` (или оставить только
   для offline), `getStreamPlaylist` для прогрева, `diskBuffer.ts` → `getStreamState`.
4. Оставить: `stallWatchdog` (сторож плеера никуда не уходит), `hlsPlaylist` для offline, `netTimeout`
   для JS API-запросов.
5. Настройки → `setConfig`: `videoCacheMB`, `reqConnectSec/reqIdleSec` (маппинг на наши пороги, с
   предупреждением «не больше 7 с для запросов плеера»), `videoCacheEnabled`, `cvhViaCache` (по
   умолчанию теперь `true`).
6. Android: `bufferConfig.cacheSizeMB = 0` при прокси; `showNotificationControls: true` для фона
   (UX-решение).
7. Офлайн-плеер: локальный URL **минуя** прокси (фикс B-08).
8. Двухнедельный rollout: pref `cacheEngine: 'ktv' | 'mediaproxy'`; KTV удаляется после приёмки;
   Dev-панель получает `getStats`/`getStreamState`.
9. Документы: новый `docs/media-proxy.md`; старый KTV-гайдлайн помечается как заменённый.

## 11. Этапы, оценки, решения

### Фаза 0 — спайки (3 дня, блокирующая)

- **S1 (1 д)**: отпечаток запросов реальных kodik/CVH через оба плеера: ходит ли AVPlayer офсетно,
  шлёт ли `bytes=0-1`, сколько соединений, принимает ли chunked, есть ли `EXT-X-KEY/MAP/BYTERANGE`, как
  ведут себя 200-на-Range и 416. Снимает главное недоказанное допущение.
- **S2 (1 д)**: жизненный цикл/порт/сеть: фон 30 с / 3 мин / 15 мин (пауза, аудио, PiP), kill, Fast
  Refresh, Wi-Fi↔LTE на IP-привязанном CVH, AirPlay. Здесь же развилка Android-FGS.
- **S3 (1 д)**: латентность 4 режимов (direct / prebuffer / tee / prebuffer+prefetch) на kodik 720p и
  CVH 1080p, 20 прогонов; критерий K1. Здесь же решение D2 (tee vs prebuffer).

**Ворота:** записаны числа; приняты D1 (свой сервер или GCDWebServer/NanoHTTPD — по умолчанию
существующие зависимости, свой только если спайк провален), D2 (tee — только если безопасен и даёт
выигрыш), D3 (FGS), D4 (пороги таймаутов).

### M1 — iOS-ядро (10–12 дней)

Скелет пакета + config plugin + TS-API; сервер по D1 (эф. порт, self-test, generation, расширение в
URL, Range/HEAD); сессии/заголовки/cookie; rewriter + pass-through; загрузчик (таймауты, префикс,
валидаторы, HTML/truncated/gzip); кэш (журнал, реконсиляция, refcount, эвикция); prefetch + `nudge` +
`getStreamState`.
**Выход:** kodik 720p и CVH через прокси, K1–K3, K6.

### M1b — устойчивость iOS (4–5 дней)

Auth/подпись/смена сети; сервер-рестарт и `onServerState`; батчинг событий; логи без тел/подписей;
полный набор тестов и конформанс в CI. **Выход:** K4, K5, K7.

### M2 — Android (8–10 дней)

То же ядро на OkHttp/NanoHTTPD (или своём сервере по D1); cleartext-конфиг; FGS-решение; отключение
SimpleCache при прокси; JVM-тесты; паритетная приёмка K1–K8. **Ворота M2:** если измерения показывают,
что `SimpleCache` уже закрывает требования (кроме движка `expo`), Android-сервер не ставим в этой
итерации — фиксируем отказ с числами.

### M3 — интеграция и приёмка (6–8 дней)

§9 целиком: адаптер, `cacheKey`, удаление warm, `diskBuffer`, Dev-панель, настройки, фон, офлайн-мимо-
прокси; два прогона приёмки (iOS, Android) по K1–K10; документы; флаг отката.

**Итого:** 31–38 человеко-дней; iOS-only MVP (M1+M1b+M3 без Android) ≈ 22–26. Это оценка после ревью —
исходные «20 дней» были нереалистичны (2 платформы + конформанс + миграция четырёх потребителей).

## 12. Адверсариальное ревью: что нашли и что изменилось

Ревью шло двумя независимыми проходами (архитектура/требования и платформы/плееры) по документам и
исходникам AnimeApp. Ключевые находки и решения:

| ID | Находка | Что изменилось в плане |
|---|---|---|
| A-01 | Кэш на `streamId` теряет прогретое при каждом ремонте/перерезолве | Введены `cacheKey` из JS + идентичность `(cacheKey, вариант, индекс, отпечаток плейлиста)`; перерезолв переиспользует кэш |
| A-02 | Наш бюджет времени длиннее сторожа (`reloadSec` 18 с) → петля ремонтов | «Ретраит плеер»: до первого байта 5 с, тишина 4 с, затем 502/504; нативные ретраи только prefetch/продолжения; тест на согласованность |
| A-03/P-07 | Лимит 8 loopback-соединений = отказ плееру | Снят; лимит только на origin; сервер ≥ 32 соединений + backlog; плейлисты вне очереди |
| A-04/P-01/P-11/P-12 | `Content-Length` как аксиома, EOF-вместо-ожидания, backpressure | Таблица состояний (§4.4), запись независима от сокета, ожидание по `writtenBytes`, абортивное закрытие, buffer-then-serve/pass-through для chunked/gzip |
| A-05/P-03 | Loopback-URL без расширения ломает выбор демуксера | Расширение в пути (`.m3u8` для плейлистов) + явный Content-Type + инвариант-тест |
| A-06 | Нет fail-open в контракте | `resolve` всегда возвращает `{url, cached}`; origin + `source.headers` как fallback; `failOpen()` |
| A-07 | Нет 400 и реакции на смену сети; IP-привязка CVH | 400 добавлен; 400/401/403/410 → `onAuthRequired`, без ретраев; смена сети — стоп, не ретрай |
| A-08 | AES-ключи осядут в дисковом кэше | Ключи только в памяти, `no-store`, отдельная ветка |
| A-09/P-13 | Нет владельца загрузки: проба `0-1` убивает, seek-шторм плодит сирот | Refcount (читатели + prefetch) + широковещательный `failed` + таймауты ожидания |
| A-10/P-14 | Эвикция во время чтения/записи | Refcount под одним мьютексом, отложенный unlink, «активный» = запрос за 2 мин |
| A-11 | Мультипликатор ретраев (наш × сторож × перерезолв) | Единый бюджет на `(cacheKey, индекс)` + cooldown; событие один раз на сегмент |
| A-13 | Не используется главный рычаг: манифест = 6.8 из 6.9 с | `resolve` предзагружает плейлист и первые 2 сегмента; сам синхронный |
| A-17/A-18 | Третье число бюджета (1 ГБ) и cap 50 %, делающий 1080p незакэшируемым | Лимит 512 МБ, один владелец, soft/hard limit, без per-stream cap |
| A-20 | Нет стратегии тестов без устройства | Чистые функции + зеркальные node-тесты + конформанс-раннер в CI |
| A-21 | `pin`, `maxAgeDays`, `altHosts`, `setHeaders`, `onPlaylist`, `onUnsupported` без потребителя | Выкинуты; failover — существующий JS-перерезолв; управление — `setConfig` + 4 события |
| Y-01 | Свой HTTP-сервер дублирует уже собранные GCDWebServer/NanoHTTPD | Спайк D1: по умолчанию существующие зависимости, свой — только по провалу ворот |
| P-02 | Наши таймауты невидимы плееру (8–10 с) | Пересчитаны от таймаутов плееров; пол скорости убран из запросов плеера |
| P-05 | 4xx наружу убивают item в Media3 | 4xx никогда не отдаём: 502/504 + событие |
| P-15/A-16 | `index.json` — это класс B-01, плюс не отличает префикс от целого | Append-only журнал + компакция, `totalLength`, усечение до коммита |
| P-19 | iOS мержит `HTTPCookieStorage` с нашим Cookie → утечка между сессиями | `httpShouldSetCookies=false`, `httpCookieStorage=nil`, свой jar |
| P-23 | «Полагаемся на сервис плеера» — а его нет (`showNotificationControls: false`) | Явный фон-контракт (§8.3): включить сервис rnv или опциональный FGS (решение M2) |
| P-31 | b64url-URL длинный и без расширения | Оставлен b64url (нужен для однозначности) + короткий `sid` + расширение; подписи в логах режем |

**Спорные места, где решение осталось прежним, но с обоснованием:**

- **Tee не выброшен полностью.** Ревью предлагало «сначала сегмент целиком, потом ответ». Это ломается
  на слабой сети: Media3 ждёт первый байт 8 с, а 0.6–3 МБ сегмента при 512 кбит/с качаются 9–48 с —
  prebuffer-only гарантирует таймаут и потерю цели «смотреть на слабой сети за счёт буфера». Оставлен
  tee с фиксами P-01/11/12/13 и режимом `serving: 'stream'|'complete'`; S3 измеряет оба.
- **Android и свой сервер.** Прятать Android в «потом» нельзя: на `expo-video` кэша нет вообще, а
  управление кэшем/лимитом/очисткой на `rnv`-движке отсутствует. Android оставлен в scope, но как M2 с
  измеримыми воротами и откатом на `SimpleCache`.
- **`EXT-X-BYTERANGE`.** В kodik/CVH сейчас нет, но проксировать (без кэша) дешевле, чем объяснять 400
  у CVH после «отдаём оригинальный плейлист».
- **AES-128.** Документы говорят, что у kodik/CVH ключей нет; поддержка оставлена как страховка (≈ день),
  потому что в запросе она есть, а стоит мало.

**Принятые риски:** tee остаётся самым сложным куском (страховка — режим `complete` и S3); поведение CDN
проверяется только S1; iOS собирается на Mac (на Windows-машине — только Android и Swift-ревью); AVPlayer
офсетное поведение не доказано до S1 — если его нет, докачка с префикса упрощается до «перекачать
сегмент», и это записано как fallback.

## 13. Допущения и открытые вопросы

1. Приложение передаёт стабильный `cacheKey` (иначе кэш живёт только в рамках сессии — но не ломается).
2. `showNotificationControls` для Android-фона — включим в приложении (UX-решение: появится уведомление
   плеера).
3. Фиксированные пороги — стартовые; финальные значения — после S1/S3, без изменения API.
4. CVH остаётся ручным по качеству (ABR не добавляем), master-плейлист проксируется как есть.
5. Приложение готово к тому, что `planStream` дёргается в `useMemo` (синхронный `resolve`), а `cacheKey`
   приходит пропом.
6. KTV удаляется не в этой же итерации, а после двухнедельного rollout за флагом.
